# LVX gem5 — Phase 0 spike

Proves the strategy in [`../PHASE0-FINDINGS.md`](../PHASE0-FINDINGS.md): the MDS
already emits LVX instruction semantics (`behavior_bodies.inc`) and the decode tree
(`Decode.c`) as portable C, coupled only to a small runtime API. We reuse that
generated C verbatim and hand-write a thin shim over the simulator engine —
here a toy CPU, in the real port gem5's `ExecContext`.

## Run

```bash
make            # extracts generated.c from ../../lvx-mds, builds, runs
```

Requires the sibling `lvx-mds` checkout (for `behavior_bodies.inc`). Point elsewhere
with `make TUPLE=/path/to/behavior_bodies.inc`.

## Files

| File | Origin | Role |
|------|--------|------|
| `generated.c` | **MDS-generated, verbatim** (regenerated by `extract.sh`, git-ignored) | `execute` bodies for `AWAIT` + register-register `ADDW` |
| `../src/arch/lvx/int256.h` | shared with the real port | `int256_t` (the spike no longer carries its own divergent copy — single source of truth) |
| `shim.h` / `shim.c` | hand-written | the runtime API the generated code calls (`operandRead`, `operandFromValue`, `idle`, …) + the fetch/execute/commit bundle engine |
| `main.c` | hand-written | harness + assertions |

## What it demonstrates

- Generated `execute` bodies compile **unmodified** (as C — they use `this` as a
  parameter name) against ~100 lines of shim.
- Correct arithmetic, including the `signextw` modifier and `sx32`/`zx32`
  result extension.
- **VLIW parallel semantics for free:** a bundle `r0=r1+r1 ; r1=r0+r0` gives
  `r1=20` (deferred write-back at the bundle boundary), not the sequential `80`.
